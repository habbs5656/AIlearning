## 第 1 步：固定随机种子

### 不改会怎样

跑两次同样的命令，loss 到小数点后第三位就不一样。你以为是哪里改错了，其实没有——什么都没变，是骰子重摇了。

### 为什么

训练开始前有**四个地方在摇骰子**：

| 摇骰子的地方                      | 在哪                    | 决定什么           |
| --------------------------- | --------------------- | -------------- |
| 卷积核初始化                      | `nn.Conv2d(...)` 建的时候 | 模型从哪个起点出发      |
| `shuffle=True`              | train.py 第 77 行       | 数据以什么顺序喂进去     |
| `random.choice(self.files)` | dataset.py 第 58 行     | 这个 patch 从哪张图裁 |
| `random.randint` + 翻转       | dataset.py 第 69–77 行  | 裁在哪个位置、要不要翻    |

这些背后都是**伪随机数发生器**：从一张"种子"出发，按公式往后算出一串数。种子不固定（默认取系统时间），所以每次的起点、顺序、裁切位置全不同，模型最后落在不同的地方，loss 就差一点点。

**为什么这很严重**：你要比较"A 配置"和"B 配置"。如果 A 自己跑两次的抖动（0.05 dB）比你 A、B 之间的差异（0.03 dB）还大，你永远测不出真差异。这叫**信噪比太低**。

### 为什么还要改 num_workers

这一条最隐蔽，也最容易白折腾一小时。

`torch.manual_seed()` 只管 torch 自己，**管不到 Python 标准库的 `random`**。而你的 `dataset.py` 第 9 行恰恰是 `import random`，裁图用的就是它。

更要命的是多进程：`num_workers=4` 时，DataLoader 会派生出 4 个子进程，每个子进程有**自己独立的 `random` 状态**，主进程的种子传不过去。

```
num_workers = 4（原来的）          主进程 set_seed(42)
                                   ├─ worker 0  ← random 状态自己初始化
                                   ├─ worker 1  ← random 状态自己初始化
                                   ├─ worker 2  ← random 状态自己初始化
                                   └─ worker 3  ← random 状态自己初始化
                                   每次跑，裁的图/位置/翻转都不一样

num_workers = 0（改完）            主进程 set_seed(42)
                                   └─ 裁图、翻转、shuffle 全在同一进程
                                   所有随机源共用一个种子
```

**最省事的解法就是 `num_workers=0`**：全部在主进程里跑，种子完全可控。数据量只有 200 张图，单进程实测约 31.5 秒/轮，这点开销换确定性很值。

### 怎么改

**文件：`train.py`**

**1.1 加 import**（第 12 行 `import argparse` 下面）

```python
import random
```

`numpy`、`torch` 原本就有，不用加。

**1.2 加 set_seed 函数**（第 24 行 `from utils import psnr` 后面，与 `def evaluate` 之间空两行）

```python
def set_seed(seed: int):
    """固定所有随机源，保证同一份代码两次跑出同一个数字"""
    random.seed(seed)                          # 管 dataset.py 的裁图和翻转
    np.random.seed(seed)                       # 管 numpy 的随机
    torch.manual_seed(seed)                    # 管卷积核初始化和 shuffle
    torch.cuda.manual_seed_all(seed)           # 管 GPU 上的随机
    torch.backends.cudnn.deterministic = True  # 让 cuDNN 用确定性算法
    torch.backends.cudnn.benchmark = False     # 关掉自动选最快算法（那个每次可能选不同的）
```

**函数体必须缩进 4 个空格**，冒号下面留空会直接报 `IndentationError: expected an indented block`。

最后两行是 GPU 的确定性开关。开了会慢约 10%，但半分钟的实验不在乎。

**1.3 加命令行参数**（第 46 行 `--lr` 那一行后面）

```python
    ap.add_argument('--seed', type=int, default=42)
```

**1.4 调用它**（第 61 行 `device = ...` 后面）

```python
    device = torch.device('cuda' if torch.cuda.is_available() else 'cpu')
    set_seed(args.seed)                      # <-- 新增这一行
```

**顺序很重要**：必须在建模型、建 DataLoader **之前**调用。放到后面只对一部分随机源生效，等于没设。

**1.5 关掉多进程**（第 47 行）

```python
    ap.add_argument('--num-workers', type=int, default=0)   # 原来是 4
```

## 第 2 步：PSNR 只算亮度通道（Y）

### 不改会怎样

你手上那个 28.93 只能和它自己比，**没法跟任何论文的数字放在一起**。

### 为什么

同一个像素有两种描述方式：

- **RGB**：红多少、绿多少、蓝多少
- **YCbCr**：亮多少（**Y**）、偏蓝多少（Cb）、偏红多少（Cr）

只是换了套坐标，不丢信息。**Y 就是亮度**，把颜色全扔掉，只留明暗。

超分领域全部只报 Y 通道的 PSNR，原因是人眼对亮度远比对颜色敏感（JPEG 能把色度砍掉一半还看不出来，靠的就是这个）。早年为省算力也只用亮度一个通道训练，沿用到今天就成了行规：SRCNN、EDSR、RCAN、SwinIR 表格里的 32.75 / 30.49 / 36.66，全是 Y 通道。

**代价有多大？** 用你 Set5 上实测的数字：

| 放大倍数 | RGB 算法 | Y 算法  | 差       |
| ---- | ------ | ----- | ------- |
| ×2   | 31.79  | 32.35 | 0.56 dB |
| ×3   | 28.62  | 29.08 | 0.46 dB |
| ×4   | 26.69  | 27.11 | 0.42 dB |

而 SOTA 模型之间的差距常常只有 0.1–0.3 dB。**换一把尺子本身移动 0.46 dB，比你要测的差距还大。** 用错尺子，排名可以直接反转。

### 先搞清楚一件事（免得白改）

**同一把尺子内部的比较，永远有效。**

你的 28.93 和 28.62 都是 RGB 算的，同一个算法、同一批图、同一个流程。所以"赢了 0.31 dB"这个结论**成立**，换成 Y，两个数一起变，差值还是 0.3 左右。

**只有跨尺子比较才无效**：拿你的 RGB 28.93 去对论文的 Y 32.75，差 3.8 dB，这 3.8 里一大半是尺子不同造成的假象。

所以改不改看你要什么：

| 目的               | 要不要改    |
| ---------------- | ------- |
| 只想看效果、看图         | 不用改     |
| 想看"赢 bicubic 多少" | 不用改     |
| 想说"我接近论文的 32.75" | **必须改** |

### 怎么改

**文件：`utils.py`（整份替换）**

```python
"""小工具: PSNR (峰值信噪比) —— 超分辨率最常用的客观指标, 单位 dB, 越高越好。"""
import math

import numpy as np


def rgb_to_y(img: np.ndarray) -> np.ndarray:
    """[3,H,W] 的 RGB -> [H,W] 的亮度 Y, 用 BT.601 权重。

    0.299 / 0.587 / 0.114 来自人眼对红绿蓝的敏感度:
    绿色最敏感(0.587), 蓝色最不敏感(0.114)。
    这套是超分论文的通行算法, 只算亮度, 不算色度。
    """
    return 0.299 * img[0] + 0.587 * img[1] + 0.114 * img[2]


def psnr(sr: np.ndarray, hr: np.ndarray, y_only: bool = True) -> float:
    """输入为 [0,1] 取值的数组, 形状一致。"""
    if y_only and sr.ndim == 3 and sr.shape[0] == 3:
        sr, hr = rgb_to_y(sr), rgb_to_y(hr)
    mse = np.mean((sr.astype(np.float64) - hr.astype(np.float64)) ** 2)
    if mse == 0:
        return float('inf')
    return 10.0 * math.log10(1.0 / mse)
```

`y_only` 有默认值，所以 `infer.py` 里原来的 `psnr(sr, hr)` 调用不用改也能跑。

### 心理预期（很重要）

**改完所有 PSNR 会整体变高，约 0.4–0.6 dB。** 从 28.62 变到 29.08 那样。

**这不是模型变强了，是换了一把尺子。** 别兴奋，也别困惑。

以后只看一个数：**`eval PSNR` 减去 `bicubic` 的差值**。差值换尺子也能比，绝对值不能。

### 踩坑

有些代码（比如 yjn870 那份）用的是 `64.738 / 129.057 / 25.064` 除以 256，那是 8bit 定点版，还带 16 的偏移（studio range 16–235）。**和 0.299/0.587/0.114 是两个版本，结果差零点零几 dB。** 不要混着用。

## 第 3 步：把 bicubic 基线打出来

### 不改会怎样

**22.34 这个数字，你不知道它算好还是算坏。**

这是最要命的一点：没有参照系，数字本身没有意义。你之前之所以卡住，就是因为手上有个数但不知道它意味着什么——直到知道 bicubic 是 22.37，才明白不但没进步，还退步了 0.03。

### 为什么能从 lr 直接拿

先看你这个任务是怎么定义的（`dataset.py` 第 37–41 行）：

```
HR（原图）──bicubic 缩小 1/3──→ 小图 ──bicubic 放大 3 倍──→ LR（网络输入）
```

**网络看到的输入，本身就是 bicubic 的成品。**

所以"bicubic 能打多少分"= 把输入原样当输出，和 HR 算一次 PSNR。不需要另写 bicubic 算法。

而且从 `EvalDataset` 里直接拿 lr，还白赚三个保证：

| 保证          | 为什么重要                        |
| ----------- | ---------------------------- |
| 同一批图        | 基线用 Set5、模型用别的，比了等于没比        |
| 同样的裁切       | 512×512 和 500×500 的 PSNR 不能比 |
| 同一个 PSNR 函数 | 两边公式不同，0.46 dB 的尺子误差就混进来了    |

如果基线自己另写一套流程，上面任何一条错了，"赢了 0.31"就是假的。

### 怎么改

**文件：`train.py`**

**3.1 加函数**（放在第 35 行 `evaluate()` 函数结束之后，空两行）

```python
def evaluate_baseline(ds: EvalDataset) -> float:
    """bicubic 基线: 网络输入 lr 本身就是 bicubic 放大的结果, 直接拿它判分"""
    total = 0.0
    with torch.no_grad():
        for i in range(len(ds)):
            lr, hr = ds[i]
            total += psnr(lr.numpy(), hr.numpy())
    return total / len(ds)
```

**3.2 在日志开头打印**（第 81 行 `log(f'eval ...')` 后面）

```python
    log(f'eval   : {len(eval_ds)} images')

    baseline = evaluate_baseline(eval_ds)                                    # 新增
    log(f'bicubic: {baseline:.2f} dB  <- 网络的起点, 也是底线')              # 新增
```

**3.3 每轮日志带上差值**（第 110–111 行，整个 log 那一句换掉）

```python
        log(f'epoch {epoch:3d}/{args.epochs} | loss {train_loss:.6f} | '
            f'eval {eval_psnr:.2f} dB ({eval_psnr - baseline:+.2f} vs bicubic) | '
            f'{time.time() - t0:.1f}s{mark}')
```

以后每一行日志自带结论，不用心算。`+0.35` 就是赢 0.35 dB，`-0.03` 就是输。

### 为什么这一步最值钱

装上基线之后，你动任何东西——换卷积核、加层数、加跳跃连接——日志每一行都会告诉你"这次改动让我离 bicubic 近了还是远了"。

**你不再需要事后翻记录、心算差额。** 这是从"能跑"到"能做实验"的分界线。

## 附：这四处和江教授那五条建议是什么关系

**先说实话：不是一一对应。** 教授提的五条里，没有"设种子""报基线""统一指标"这些。

他提的五条是**研究对象**：

1. 数据集的读取与预处理
2. 卷积核大小对结果的影响
3. 网络层数对结果的影响
